# Optional app integration preparation

Public app/Auth delivery grants no integration setup authority. The additive
`app-integrations-capability-plan-v1` contract names the existing normal Builder
project, exact captured app release and prior approved resource operation. It
separately freezes the dedicated development control resource, fixed schema and
worker, declared service actor scopes, Sandbox recipe/provider facts, trusted
profile digest, and opaque private-configuration seed reference/hash.

The four ordered effects prepare the control database, install its fixed
schema with restricted grants, bind only the declared service memberships, and
register the app's exact central service/catalog/setup authorities through the
existing control plane. Registration must use an atomic app-scoped authority
record, never a shared environment-map overwrite.
They do not create an application project, assign Auth users, activate a
provider, or release source. Every effect needs a fresh ordinary approval and
actual readback under the existing native operator/journal/physical lease.
Unknown dispatch outcomes remain unknown; absence alone never authorizes retry.

The complete strict outer plan is encoded as recursively ASCII-key-sorted JSON;
array order is preserved. Its SHA256 is the effect approval digest and determines
the operation reference. A fixed worker validates this full digest before
deriving its narrower resource/schema/service projection. A bootstrap projection
or private configuration reference never substitutes for complete plan approval.

Only the control migrator credential may be shared through exact owner-scoped
dedicated development database/migrator custody. Each app receives a distinct
CP runtime login with immutable SESSION_USER app/tenant scope; shared central
CP logins and broad provider API credentials remain in platform infrastructure.
App service, catalog, and setup-proof secrets
remain app-owned. A shared unrestricted control-database login cannot be projected
into generated apps; the capability must establish a nonforgeable app/tenant
SQL scope or an equivalent central lease protocol before runtime readiness. The Production control-database exclusion and provider-secret
references come only from protected deployment-owned configuration.

The optional delivery projection consists of exactly
`APP_INTEGRATIONS_CAPABILITY` and `APP_INTEGRATIONS_RUNTIME_CONFIGURATION`.
It has its own concrete approved capability reference and loaded/readiness
proof. It is independent of the fifteen-key Auth fingerprint and cannot be
silently appended to an existing frozen public-release plan. Provider connection,
canonical data, tenant isolation, and lifecycle acceptance remain separate.
The four effects use the existing provisioning journal and global physical-resource
fencing sequence. A dispatched effect is durable before its worker starts. Lost
acknowledgments stay pending; only an authoritative effect-specific nonapplication
proof permits another dispatch, retaining the earlier attempt. Accepted SQL actor
and control-principal generations remain independent of a later lease generation.
The fourth effect requires atomic per-app SQL scope plus encrypted central authority
registration, followed by exact independent readback; scope-only registration is
insufficient.

Plans also retain the captured executable provider read configuration and its
canonical digest, the original checked-release artifact, separate control Neon
identity, and the exact approved central-host setup/caller receipts. Optional
machine paths come from the captured installer metadata. Public Auth's fifteen-key
runtime proof remains separate from integration configuration and SQL readiness.
These core contracts do not themselves establish that native composition or hosted
acceptance has completed.
The native operator mounts `/v1/app-integrations`; ordinary internal Builder tools
plan and separately approve its four effects. Its protected deployment profile
`PROTECTED_APP_INTEGRATION_CAPABILITY_PROFILE` supplies `version:1`, an `id`, the
fixed `controlSchema` artifact/hash, the pinned `worker` id/hash, and per-app
`applications` entries containing a distinct `controlRuntimeRole` and the declared
`serviceMemberships`. Only the selected app entry and global fixed artifacts enter
that app's profile digest; adding another app does not retarget earlier plans.
The operator independently resolves the normal app destination and checked source.
A missing profile, exact central caller receipt, protected connection reader, or
pinned worker reports a bounded actionable prerequisite.

The first app seed is encrypted under app/normal-provisioning/control-resource
custody and reused across ordinary revisions. It holds only this app's restricted
control password and purpose-separated app keys. Runtime configuration and sealed
central registration use separate immutable checkpoints derived from the approved
plan and independently accepted actor/principal generations. The shared central
migrator/keyring remain in central setup custody; they never enter app runtime
configuration. The native adapter uses the existing protected installer transport.
