## Operating rules for continuation

- **Fixed scope:** choose one outcome and stopping condition. Surface additional discoveries in the deferred inventory; do not improve on the fly or convert every observation into another gate. Give wall-clock estimates only after checking actual dependencies and owner capacity; distinguish elapsed time, parallel effort and external waiting. No credible single completion estimate exists for all optional work without a selected scope.
- **Approval:** continue ordinary technical repairs within the already-approved effect without asking for confirmation per commit. Preserve server-settled approval evidence, owner/tenant boundaries and uncertainty reconciliation. New actors, materially new effects, recurring billing, destructive actions or Production scope need their applicable authority. Prior credit/storage approvals are not unlimited spending authority.
- **No app-content gates:** assert actual Builder behavior, security/cross-user isolation, unapproved outward effects and real provider/repository failures. Do not assume role count, app schema/layout, source shape, package version/path, quota or score. User-authored app tests may express that app's requirements; do not invent universal app requirements.
- **Fast iteration:** follow AGENTS.md and [local lifecycle](local-development-lifecycle.md). No automatic broad tests, fresh installs, builds or hosted walkthroughs after every edit. Use a focused check only for a concrete repair; final acceptance and exact-head CI are distinct. Existing approval permits landing scoped repairs without waiting for CI, while recording and addressing actual final failures.
- **Workflow ownership:** all generated-app changes go through the supported public Builder. Preserve one public session and its cursors/replies; never silently replace it. One coordinator integrates, publishes and performs provider mutations; independent agents return bounded commits or blockers. Avoid duplicate writers and speculative verification lanes.
- **Workspace safety:** the original shared Builder checkout contained unrelated local changes and stale branch state. Do not reset, clean or commit it wholesale. Refresh remote heads and use an isolated checkout. Temporary task clones are not canonical evidence or disposable by default. Keep dependencies/caches outside source; use the supported development entrypoint when development is actually needed.
- **Publication credentials:** local CLI auth and connected GitHub app permissions differ. The Arrusted workflow push lacked OAuth `workflow` scope; the connected GitHub tool published the exact reviewed signed commit. Do not rotate credentials or claim deployment failure from that local CLI limitation. Verify actual ref/commit/blob readback after publication.
- **Infrastructure:** Vercel Sandbox is the execution backend, project-scoped OIDC the credential boundary, with allow-all networking. Drives retain data when compute stops. Provider inventory/READY status is not semantic hosted proof. Do not migrate, delete or recreate resources merely to refresh this handoff.
- **Presentation:** short familiar user text, headings/bullets and a clear next action; explain material access/cost/retention effects. Keep hashes, provider plumbing and diagnostic dumps out of primary user copy.
