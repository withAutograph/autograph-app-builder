# Continue correction of an unapplied declined proposal

A genuine user correction can inspect the current frozen draft and then stop
without producing a corrected proposal. The accepted-intent authoring lane
currently stops whenever any proposal exists. Extend that lane only for the
following observed correction boundary; do not reset the workflow or grant.

The current proposal must be an unapplied existing-app plan with exact accepted
AppSpec, owner/session, source and workspace bindings. A complete retained native
`denied-not-run` decision must name that exact proposal and scope. An absent card,
an empty pending list, assistant text, ignored/invalid decisions, or denial of a
different proposal cannot establish this condition. A matching execution grant
or any unresolved pending approval blocks correction continuation.

A new genuine external user message must arrive after that denial is already
retained. An authenticated internal authoring/build marker and an approval-only
resolution are not new user requests. The same external turn must successfully
inspect the explicitly selected current-proposal source. Retain the first such
inspection for that request, so more reads cannot reset the no-progress fence.
This is an observation of drafting work under accepted product intent; it does
not classify prose as execution consent or change the product requirements.

Bind the authoring continuation to the current proposal digest, exact denial
evidence digest, new user event identity and message hash, first inspection call,
and the existing accepted AppSpec/source/workspace scope. Preserve the original
proposal, denial and historical grant. The normal controller may dispatch one
owner-bound drafting message. If that internal turn leaves the proposal and scope
unchanged, retain the existing typed no-progress block. A successor proposal stops
this correction lane and needs its own ordinary fresh Build approval. Pending
questions/approvals, cancellation, failed or uncertain calls, changed owner or
source, and current approved execution remain blocking boundaries.

The authenticated internal correction turn cannot request Build for its unchanged
declined proposal. That tool call receives a read-only corrected-proposal
prerequisite before approval registration or implementation. A genuinely new
external request and a corrected successor proposal retain their ordinary fresh
Build path; the guard does not treat either as previously approved.

Existing accepted-without-proposal behavior and frozen decision shapes remain
compatible. Add only an optional correction binding to the drafting scope; do not
widen approved-build schemas, fabricate tool results, clear native authority,
resend approval responses, or infer provider settlement. Keep source changes in
shared Builder workflow code; generated app files remain Builder-authored.

Qualification covers genuine denial lifecycle events plus real external-message
and successful proposal-inspection observations, unchanged planned cards, missing
or foreign denial, grant/pending/unknown refusal, marker forgery, same-scope
no-progress, successor proposal/fresh approval, cancellation, and local/hosted
controller/store compatibility. Source tests do not establish real app behavior.
A runtime that missed the old observation must receive a fresh ordinary user turn
or reconstruct genuine native events through an independently qualified path;
never invent an observation from a saved summary.
