public delivery, BetterAuth access and same-project revision. Third-party user-app

work and are not prerequisites for this milestone. Preserve their source,
resources, receipts and unresolved effects.

optional integration declaration through ordinary Builder authoring; do not
bypass installed-capability or retention checks. An unavailable capability must
not appear connected or successful. Verify actual app behavior, public Auth,
tenant isolation, persistent data and a same-destination revision. Full A-469
integration acceptance remains open until its deferred criteria are exercised.

The catalog and runtime must use one explicit selected source, with source,
lockfile, catalog, worker and runtime evidence aligned. Keep local Builder for
development and preserve the original recovery session and uncertain operations.
Any release or resource effect requires its own concrete authorization.

## Confirmed cross-layer gaps to close together

1. **Recover actual completed source transport provenance.** Earlier
   `prepare_workspace` copied source and returned new metadata while retaining
   the old workflow phase and workspace. `workspace_status` reports observed
   metadata, which is not the workflow's durable source baseline. Recover the
   genuine completed native tool result for the same owner/session/workspace,
   rather than trusting candidate metadata or replacing old plan provenance.
   Add a regression through the workflow adapter and actual history shape.
   **Correction from the execution audit:** the qualified continuation in turn
   17 read historical workflow status; it made no new planning, reconciliation,
   validation or preview call. Its retained revision marker did not prove a
   stale callback was dispatched. The last actual reconciliation failure was
   in turn 16. Do not introduce a cache bypass or rewrite checkpoints on that
   evidence. Verify new-idle-turn versus in-flight generation selection through
   actual dispatch, and report current attempts separately from historical
   failures. The source-history reader must use the same verified local recovery
   profile and must not silently downgrade to incomplete ancestor history when
   its cycle variable is missing. See the
   [execution alignment audit and plan](2026-11-03-builder-execution-alignment.md).

2. **Connect the development execution path to actual release capabilities.**
   The current private local launcher disables publication/bootstrap and does
   not forward the protected operator endpoint. The effect clients require an
   authenticated owner and protected HTTPS operator. The local adapter creates
   native sessions without forwarded user/workspace authority or canonical SQL
   session registration; project OIDC proves the machine, not the user. No
   effect-capable local profile was found. The selected route is to keep local
   runs for development and qualification, then use one bundled shared release
   for the final hosted flow. Adding an authenticated local delivery mode is not
   part of this repair batch. Re-read the genuine hosted owner/session and
   pending actions before continuation; do not flip flags, invent claims, copy
   approvals or silently transplant the private local app. Editing a local
   factory does not update the remote operator.

3. **Finish central integration composition.** Approved service/provider/tool
   implementations and private custody exist on isolated branches, but their
   actual native endpoint, resources/schema worker adapters, captured source cut
   and fixed worker artifacts, source publication,
   owner/history readers, webhook receiver, ready/private/control-bootstrap ports
   and app-capability consumers must be assembled and tested together. Missing
   private profile/configuration remains explicit, never a fixture success.
   The audit found the outer operator composition dropped public-release and
   app-capability ports even when their factories constructed them. Verify
   positive requests through the actual default factory and mounted routes,
   including the new central port. Independently read the installation,
   repository and reviewed source before proposing setup effects. A separate
   revision session must read and verify the original ready caller/setup and
   their original consent, not create a replacement or transfer approval.

   Package the exact three directly executable worker files, receipt and
   Git-inventoried source into an offline code-only artifact outside the live
   planning checkout. Verify direct execution on the actual Linux Sandbox base,
   including Bun availability and protected SQL transport. Running `bun file.js`
   on a developer Mac does not prove the SDK's direct-executable command works.
   The three-worker bundle is additive. Preserve and verify the full existing
   installer catalog from a fresh trusted worker base, then overlay the new
   source. Standard app resource profiles select their own Sandbox filesystem;
   updating only the base operator configuration leaves them unchanged. Verify
   each intended base/profile selection before the bundled release.

   Compiled native ingress inspection also found two missing Vercel Services
   rewrites despite mounted central handlers, and a pinned Bun compiler parsing
   failure missed by source tests/types. Exercise actual provider route-table
   resolution into the compiled operator, as well as service-level composition.

4. **Provide reachable authenticated native delivery receipts.** A provider
   webhook cannot reach a loopback Mac endpoint. Identify the supported public
   callback and its actual runtime/configuration release. Preserve immutable
   accepted deployment IDs; no listing/SHA/time selection or manual promotion.
   Any shared operator release must be a concrete separately reviewable action.
   Builder's public callback relays through the closed authenticated operator
   transport. Only the separate operator verifies the provider signature and
   persists the receipt; Builder must not load the operator's privileged private
   configuration merely to receive a webhook.

5. **Complete optional-capability removal handoff.** Shared source uninstall and
   backend disable/drain already exist. The Builder release/revision contract
   does not yet freeze and execute their ordered handoff. Drain and independently verify stopped
   app work before removing source verification routes; preserve the peer app,
   shared connection, canonical data and history. The default release should
   explicitly retain the two exact previously owned optional environment rows
   read-only as a disabled tombstone, with no integration-readiness claim and
   with independently verified authority fencing. Exact environment deletion or
   credential/principal cleanup needs a separate concrete cleanup scope. Reuse
   the existing lifecycle; source omission alone is not a completed removal.
   The fixed approved worker must use the existing strict protected-connection
   checks, preserve principal/authority then connection/binding lock ordering,
   and persist an app-specific fence receipt for reconciliation after its old
   app credential is denied. Current consent and the held physical lease remain
   checked at each effect boundary without recursively acquiring the same SQL
   locks. A rejected app credential alone is not stopped-work proof.

6. **Correct the consumed integration authoring guidance.** The Builder reference
   still names a generic host plus platform adapters instead of the existing
   configured shared Next host, and omits required `readObjects` and
   `checkedRelease` fields. Correct the shared reference and its generated
   bundle/parity through the supported task, rather than repairing generated
   app files on Builder's behalf.

7. **Close the central machine runtime environment.** The current central-only
   catalog still emits the platform Shell and the standard eager Gateway.
   Gateway startup needs additional platform identity/origin configuration that
   the central integration environment does not provide. Human Shell/Auth paths
   have further requirements. Implement an explicitly reviewed central-machine
   Services composition containing Gateway and Integrations, without Shell/Auth.
   Keep the existing neutral Gateway and MIT library as the final composition
   plane; allow only the exact signed readiness/control/provider-read lanes and
   deny browser/session/Auth/unrelated routes. Declare the mode in the approved
   source/manifest; never infer it from absent keys. Do not inherit customer Auth
   keys or add default Production fallbacks. Probe the actual compiled entrypoint
   with only declared central bindings and provider-owned native metadata.

   Independent provider readback found the configured central target is the
   shared `apps` project with inherited unscoped Preview credentials. It is not
   an isolated central target. Stop before setup effects when inherited secrets
   violate the central profile. Resolve the actual infrastructure destination
   explicitly; do not blank inherited values, modify customer environments or
   create an arbitrary replacement acceptance project. The generated app still
   uses its one ordinary Builder-owned destination.

## Further handoffs within this same repair batch

The following concrete source findings extend groups 2 and 3 above. They must
be repaired before the one shared release; they are not reasons to run another
live effect or reinterpret an existing approval.

- **Authenticated browser bindings after public delivery.** Normal resource
  setup ends at `resource-ready`, while the old browser lane requires `bound`
  and a delivered protected Preview candidate. Add an explicit verified public
  delivery projection from the exact READY application release, selected normal
  destination, runtime checkpoint, current owner, original/current consent and
  live Auth/runtime observation. Use its public origin and real selected actor
  jars for normal authenticated browser tests. Preserve the old Preview
  projection; do not relabel it as Production or invent a Preview deployment.
- **Real provider delivery destinations.** An app's `readObjects.destination`
  is currently an opaque name. Normal setup neither resolves its actual
  Ampersand webhook URL nor reads back its signing key, and the central reader
  uses one global key. Add an explicit new capability version with a concrete
  approved `prepare-provider-destination` effect. Freeze the exact provider
  project/name and source-owned app ingress/public origin. Read the named
  destination first; create once only when absent, seal its accepted identity
  and key before acknowledgement, then independently read back the same
  resource. Do not retarget a mismatched existing destination or resend an
  uncertain create. Keep each destination's key encrypted and central-only;
  verify delivery with the exact registered app/provider authority. Preserve
  legacy global mode and all frozen v1 effects. Publish and verify the public
  app before human Connect/Activate can cause provider reads.
- **Integration-only resource worker selection.** Both integration setup
  adapters currently select the generic `resourcesWorker`, which is also used
  by unrelated Auth/app setup. Add a separate integration resource descriptor
  instead of replacing that legacy worker globally. Central setup already pins
  its resource executable; the new app capability version must also freeze its
  resource worker identity/hash. Resolve only the exact approved artifact from
  the trusted catalog. Old v1 operations retain their original selection and
  meaning; absent or mismatched artifacts remain a prerequisite. Coordinate
  this field with the capability version and final selected image/profile cut.
