# Public app release through Builder

The normal Builder app keeps one owned Services project at the repository root.
`plan-app-public-release` resolves the current saved app's normal provisioning
receipt, reviewed published source, independently verified ready synthetic
runtime, public origin and Production branch. Its plan freezes the exact
restricted runtime environment keys and value hashes; credentials remain behind
an opaque authority-bound configuration reference in the protected adapter.
The current supported pilot uses development provider resources and synthetic
app/Auth records. It does not authorize customer Production integration activation.

`release-app-public-release` asks for ordinary consent naming two ordered
effects: bind the named runtime configuration in that same project's Production
environment, then publish the reviewed source using normal Git delivery. The
protected service independently verifies complete current-call consent, current
owner/provider authority and the exact frozen plan before effects. An earlier
cancellation dominates a later approval for the same plan. The five public
Builder tools are unchanged. Old protected Preview operations and approvals are
not converted into public-release authority.

This operation uses the existing provisioning journal table under the separate
`public-app-release-v1` record kind and the existing physical-resource lease.
Each environment key is claimed before dispatch; its accepted provider row ID
and independent verification checkpoint in the same record. A lost response
without a row receipt stays unknown. A matching name or absent row does not
prove the effect did not happen. Reconciliation uses effect-specific trusted
readback and never blindly resends a create, source publication or uncertain
public response. Revised bindings explicitly name their prior owned row ID,
operation and value hash; foreign rows are not adopted or overwritten.

The release path does not call Vercel deployment creation, promotion or alias
mutation. Native Git delivery owns deployment and activation. Read-only
observation follows the provider's currently active Production domain/deployment
binding; it does not select by Git ancestry, source SHA, list order or time.
The normal public domain opens without Vercel sign-in. BetterAuth and app
assignment/tenant authorization still protect application behavior. A deployment
observation does not establish login, persistent actions or provider ingestion;
the result retains `authenticatedBehavior: "unassessed"` until the app's actual
accepted journey is exercised.

The consumed operator composition must provide real authoritative receipt,
synthetic-runtime, private configuration, approval-history, environment,
publication and active-domain adapters. Missing capabilities fail closed; local
port tests are recovery evidence, not hosted product acceptance.

## Source publication and provider binding

The source publication plan freezes the reviewed source commit and the expected
current Production branch commit. The GitHub adapter uses an atomic expected-OID
reference update with `force: false`, followed by an independent reference read.
A moved branch requires a new plan; Builder never forces it or silently merges
unreviewed content. A lost publication response is reconciled read-only. Once
dispatch may have occurred, observing the old branch does not authorize retry.
These Git facts govern the approved source write only, never Vercel deployment
selection or Gateway activation.

The private Vercel adapter preflights all runtime values and prior binding
ownership before writing any key. It accepts only encrypted, Production-only
rows, excluding branch, custom-environment and Marketplace bindings. It records
each accepted row ID and verifies the decrypted value privately. Public results
contain no environment values. Delivery observation reads the provider's active
Production target and public-domain alias, verifies the actual installed release,
and then rechecks activation before reporting delivery ready.
